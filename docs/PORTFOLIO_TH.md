# ใช้โปรเจกต์นี้พัฒนาทักษะและเล่าตอนสัมภาษณ์

NNT Client Portal เป็นตัวอย่างเว็บที่มีผู้ใช้สองบทบาทและข้อมูลจริงในฐานข้อมูล จุดที่ควรฝึกคืออธิบายเหตุผลของการออกแบบ แล้วทดลองแก้ระบบด้วยตัวเอง ไม่ใช่จำชื่อเทคโนโลยีอย่างเดียว

## โครงเรื่องของโปรเจกต์

> ผมทำระบบให้ฟรีแลนซ์สร้างโปรเจกต์จาก brief เชิญลูกค้าเข้ามาติดตามงาน แลกไฟล์ ให้ feedback และอนุมัติ milestone ได้ โดยแยกสิทธิ์เจ้าของ workspace กับลูกค้าของแต่ละโปรเจกต์

ใช้คำอธิบายนี้เมื่อเข้าใจและได้ทดลองระบบแล้ว บอกตามจริงว่าส่วนใดทำเอง ส่วนใดพัฒนาร่วมกับ AI และชี้ส่วนที่คุณอ่าน แก้ และทดสอบได้ หลีกเลี่ยงการอ้างว่าเป็นระบบธุรกิจที่เปิดใช้งานจริงหากยังเป็นเดโม

## ทักษะที่ควรอธิบายให้ได้

| เรื่อง | คำอธิบายที่ควรฝึก | หลักฐานที่ทำให้เห็นได้ |
| --- | --- | --- |
| Frontend | หน้าจอรับข้อมูลและตอบสนองต่อ loading, empty, error อย่างไร | สร้าง project แล้ว refresh; ทดลองกรอกข้อมูลผิด |
| API | ทำไม frontend ส่ง request แล้วให้ server ตรวจซ้ำ | เปิด Network ดู request และ response ของการสร้าง task |
| Authentication | session บอกว่าใครกำลังใช้งานอย่างไร | ลงชื่อเข้าใช้ ออกจากระบบ และลองเรียก endpoint เดิม |
| Authorization | ทำไมลงชื่อเข้าใช้แล้วจึงยังอ่านทุกโปรเจกต์ไม่ได้ | เปิดสองบัญชีและทดลองอ่านโปรเจกต์ที่ไม่ได้รับเชิญ |
| Database | workspace, project, task และสมาชิกสัมพันธ์กันอย่างไร | อธิบาย schema และ SQL migration ที่สร้างตาราง |
| File storage | ทำไม metadata อยู่ D1 แต่ไฟล์อยู่ R2 | ไล่ flow อัปโหลดและดาวน์โหลดโดยไม่เปิด bucket เป็น public |
| Business rules | ทำไม client อนุมัติได้เฉพาะ milestone ที่ ready | ทดลอง pending → approve แล้วอธิบายการปฏิเสธ |
| Deployment | source บน GitHub ต่างจาก backend ที่กำลังรันอย่างไร | อธิบาย build, binding, migration และ environment secret |

## แนวคิดสำคัญที่ได้จากโค้ด

**แยกตัวตนออกจากสิทธิ์** — Better Auth ตรวจว่าผู้ใช้คือใคร ส่วน portal ตรวจว่าเขาเป็นเจ้าของ workspace หรือสมาชิกของโปรเจกต์นั้นหรือไม่ การซ่อนปุ่มใน frontend ไม่เพียงพอ

**เก็บเงินเป็นจำนวนเต็ม** — `budgetCents` เก็บหน่วยสตางค์ เช่น `125050` คือ 1,250.50 บาท ทำให้ไม่ต้องบวกลบเลขเงินด้วย floating point

**ลิงก์เชิญเป็นความลับ** — token ใช้ครั้งเดียวและหมดอายุ ฐานข้อมูลเก็บ hash ไม่เก็บ token ดิบ สิทธิ์เกิดจากการถือ token ไม่ใช่อีเมลที่กรอกใน brief

**อย่าเชื่อชนิดไฟล์จากชื่ออย่างเดียว** — server จำกัดขนาดและตรวจข้อมูลไฟล์ที่รองรับ แล้วให้ดาวน์โหลดผ่าน endpoint ที่ตรวจสิทธิ์ ไฟล์จึงไม่ต้องมี public URL

**migration ทำให้ฐานข้อมูลสร้างซ้ำได้** — schema ไม่ควรถูกสร้างแบบกระจัดกระจายในทุก request และข้อมูลตัวอย่างควรแยกจาก migration

## เช็กลิสต์ก่อนใส่ในเรซูเม่

- [ ] รันจากการ clone ใหม่ได้ตาม README โดยไม่ต้องคัดลอกไฟล์ลับจากเครื่องเดิม
- [ ] ทดลอง owner และ client คนละ browser profile แล้วอธิบายความต่างได้
- [ ] สร้าง project/task/comment แล้ว refresh ข้อมูลยังอยู่
- [ ] บัญชีที่ไม่ได้รับเชิญอ่านและแก้โปรเจกต์คนอื่นไม่ได้
- [ ] client อนุมัติ milestone ที่ ready ได้ และอนุมัติ pending ไม่ได้
- [ ] ไฟล์ที่อัปโหลดดาวน์โหลดได้เฉพาะคนที่มีสิทธิ์ และไฟล์เกินขนาดถูกปฏิเสธ
- [ ] อ่าน test สำคัญได้อย่างน้อยหนึ่งชุด และแก้โค้ดเล็กน้อยแล้วตรวจผลเองได้
- [ ] มีภาพ desktop/mobile และคลิปเดินระบบสั้น ๆ จากข้อมูลตัวอย่าง
- [ ] README ระบุสิ่งที่ทำได้ ข้อจำกัด และขั้นตอนรันอย่างตรงไปตรงมา
- [ ] ไม่ใส่ข้อมูลลูกค้าจริง รหัสผ่าน token หรือไฟล์ที่เป็นความลับใน repo

เช็กลิสต์นี้เป็นเป้าหมายการเรียนรู้ ไม่ใช่รายงานว่าได้ผ่านทุกข้อแล้ว ผลตรวจจริงต้องอ้างจากการรันระบบและรายงานทดสอบของเวอร์ชันนั้น

## ตัวอย่างข้อความในเรซูเม่

เมื่อคุณทดสอบและอธิบายระบบได้แล้ว ปรับข้อความนี้ให้ตรงกับส่วนที่คุณรับผิดชอบจริง:

> Developed a freelance client portal with project-scoped access, task and milestone tracking, client feedback, and private file uploads using React, TypeScript, Better Auth, Drizzle, D1, and R2.

เพิ่มจำนวน test หรือผลวัดประสิทธิภาพได้เมื่อมีหลักฐานการวัด ห้ามแต่งจำนวนผู้ใช้ อัตราลดเวลา หรือผลลัพธ์ทางธุรกิจจากข้อมูลเดโม

## งานฝึกต่อหลังเข้าใจ MVP

เลือกเพิ่มทีละข้อหลังจาก workflow เดิมยังทำงานครบ: แก้ไข brief โดยมีประวัติการเปลี่ยนแปลง, กรอง activity ตามประเภท, หรือเพิ่มการทดสอบสิทธิ์ใหม่หนึ่งกรณี ก่อนต่อระบบภายนอกควรเข้าใจขอบเขตข้อมูลและค่าใช้จ่ายของบริการนั้นก่อน
